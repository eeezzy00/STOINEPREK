## 1. Что это за игра

2D action-платформер с боевой системой на парированиях. Референс по управлению и ощущениям — **Katana Zero**. Визуал сместился от изначального «dark fantasy» к **неоновому ночному городу** (розово-фиолетовая палитра, самураи, синтвейв).

- **Движок:** Godot 4.7.2 stable, рендер Forward+, драйвер D3D12
- **Спрайты:** пиксель-арт, `default_texture_filter = 0` (nearest), включён snap 2D transforms/vertices — пиксель-перфект настроен
- **Разрешение:** stretch mode `canvas_items`, aspect `expand`
- **Физика:** `physics_interpolation = true`

**Как ведётся разработка:** пользователь — не программист, работает через AI-ассистента. Код пишет ассистент, пользователь ставит задачи, тестирует и принимает решения по геймдизайну. Язык общения — русский.

## 2. Текущий боевой баланс (реальные значения из кода)

### Игрок — `player.gd`

| Параметр | Значение | Примечание |
|---|---|---|
| `max_hp` | 3.0 | |
| `attack_damage` | 1.0 | базовый урон до модификаторов sweet spot (см. ниже) |
| `attack_speed` | **0.5 с** | максимум 2 удара/сек |
| `strike_range` | **50 px** | ширина хитбокса |
| `HITBOX_HEIGHT` | 60 px | константа, синхронизирована с debug_visualizer |
| `move_speed` | 250 px/с | целевая скорость, реально достигается через разгон (см. ниже) |
| `attack_startup` | 0.15 с | задержка до активных кадров |

**Разгон/торможение (новое).** Раньше `velocity.x` присваивалась мгновенно. Теперь едет через `move_toward` с разными темпами:

| Параметр | Значение |
|---|---|
| `ground_acceleration` | 3200 px/с² |
| `ground_friction` | 4000 px/с² |
| `air_acceleration` | 1800 px/с² (в воздухе управление более "рыхлое") |
| `air_friction` | 1400 px/с² |

На земле топ-скорость набирается меньше чем за 0.1 с — ощущается почти как раньше (мгновенно), но без резкого рывка на старте/остановке.

**Прыжок:**

| Параметр | Значение |
|---|---|
| `jump_velocity` | 445 px/с |
| `jump_gravity` | 900 px/с² |
| `max_fall_speed` | 1400 px/с |
| `coyote_time` | 0.1 с |
| `jump_buffer_time` | 0.1 с |
| `jump_cut_multiplier` | **0.45** (новое) |

Пиковая высота прыжка = `445² / (2 × 900)` ≈ **110 px** (при полном удержании кнопки).

**Короткий прыжок (short hop, новое).** Если отпустить `jump` пока `velocity.y < 0`, вертикальная скорость умножается на `jump_cut_multiplier` — короткое нажатие даёт низкий прыжок, удержание — полную высоту (как в Celeste/Mario). Действует и на wall-jump.

**Стена — wall-slide / wall-jump (новое, из последнего коммита):**

| Параметр | Значение |
|---|---|
| `wall_slide_speed` | 90 px/с (клэмп скорости падения у стены) |
| `wall_jump_speed_x` / `wall_jump_speed_y` | 380 / 420 px/с |
| `wall_jump_control_lock` | 0.15 с — управление по X заблокировано после отпрыга |
| `wall_coyote_time` | 0.1 с |
| `max_wall_jump_chain` | **2** — подряд идущих wall-jump без касания земли, дальше отпрыг не срабатывает (иначе можно бесконечно скакать между двумя стенами вверх) |

Прилипание к стене происходит только когда игрок в воздухе, касается стены и жмёт **в неё**; если жать от стены или ничего не жать — соскальзывает обычным падением.

**Перекат:**

| Параметр | Значение |
|---|---|
| `dash_duration` | 0.2 с |
| `dash_distance` | **60 px** |
| `dash_cooldown` | 2.0 с |
| `double_tap_window` | 0.3 с |
| `dash_attack_cancel_ratio` | **0.6** (новое) |

Перекат можно вызвать двумя способами: клавишей `dash` или **двойным нажатием** влево/вправо.

**Отмена переката в атаку (новое).** После 60% длительности переката (`dash_attack_cancel_ratio`) нажатие атаки обрывает перекат и сразу запускает выпад-удар вместо того, чтобы просто проглатывать нажатие до конца переката. Это первый (и пока единственный) официальный "cancel" в новой стейт-машине игрока (см. ниже).

**Зоны попадания / Hit Zones (новое — раньше это был пункт "не сделано").** У удара теперь не мгновенная проверка, а окно:

| Параметр | Значение |
|---|---|
| `attack_active_duration` | 0.12 с — сколько кадров подряд хитбокс продолжает проверять цель после startup |
| `sweet_spot_ratio` | 0.35 — доля окна, которая считается "sweet spot" |
| `sweet_spot_damage_multiplier` | ×1.5 |
| `late_hit_damage_multiplier` | ×0.75 |

Раньше попадание проверялось один раз, ровно в момент окончания startup — если цель не оказывалась в хитбоксе именно в этот кадр, весь удар считался промахом навсегда. Теперь окно "живое" 0.12 с: попадание в первые 35% окна — усиленный удар (×1.5), позже — ослабленный (×0.75). Полный промах (никто не зашёл в хитбокс за всё окно) логируется в телеметрию как раньше. То же самое зеркально реализовано у врага (см. ниже).

**Стейт-машина игрока (новое).** Формальный `enum PlayerState { GROUNDED, AIRBORNE, WALL_SLIDE, DASH, ATTACKING, HURT, DEAD }` с явной таблицей допустимых переходов (`TRANSITIONS`). Не заменяет старые булевы флаги (`_is_attacking`, `_is_dashing` и т.д. — на них завязана рефлексия в `admin_panel.gd`, `debug_hud.gd`, `samurai_npc.gd`), а работает параллельно как источник истины для вопроса "можно ли сейчас прервать текущее действие действием X". Пока единственное новое правило, которое она реально разблокировала — dash → attack (см. выше).

**Ощущение приземления (game feel, новое).** Жёсткое приземление (`fall_speed >= landing_min_fall_speed = 250 px/с`) триггерит: сжатие спрайта (squash/stretch, `landing_squash_scale = (1.25, 0.75)`, пружинит обратно за `landing_squash_duration = 0.12с`), пыль под ногами (`landing_dust`, частиц 6–16 в зависимости от силы удара) и лёгкий "просад" камеры вниз (`landing_dip_amount = 8px`, восстанавливается с той же экспонентой, что и `camera_lead`). Мелкие спрыгивания со ступеньки эффект не триггерят.

**Парирование:**

| Параметр | Значение |
|---|---|
| `parry_late_limit_frames` | 10 кадров |
| `max_parry_charges` | 3 |
| `parry_regen_interval` | 3.0 с |
| `perfect_streak_for_bonus` | 3 |
| `normal_hit_hitstop_frames` | 2 |

**Формула отката (актуальная):**
```gdscript
knockback = maxf(12.0, 55.0 - (frames_late / 10.0) * 40.0)
```
Диапазон **12–55 px**. Раньше был 15–80 px, но с настоящей гравитацией такой откат сбрасывал игрока с платформы — сузили осознанно.

**Градация парирований:**

| Опоздание | Тир | Hitstop | Стоимость заряда | Искры (цвет / кол-во) |
|---|---|---|---|---|
| ≤ 2 кадра | PERFECT | 6 кадров | 0 | золотой / 50 |
| ≤ 5 кадров | GOOD | 4 кадра | 1 | белый / 34 |
| ≤ 8 кадров | LATE | 2 кадра | 1 | серый / 24 |
| ≤ 10 кадров | BARE | 1 кадр | 1 | тёмно-серый / 16 |
| > 10 кадров | MISS | — | — | урон игроку |

Проверка парирования **симметричная**: сравнивается момент активных кадров игрока с моментом активных кадров врага, `absf(now - enemy_active_time) * 60`. Опоздать и поторопиться — одинаково.

Три PERFECT подряд → `_next_hit_bonus = true`, следующий удар **×2 урона**, спрайт подсвечивается золотым.

**Зоны попадания у врага (новое, зеркально игроку):** `attack_active_duration = 0.12с`, `sweet_spot_ratio = 0.35`, `sweet_spot_damage_multiplier = ×1.5`, `late_hit_damage_multiplier = ×0.75`. Окно открывается после `PARRY_GRACE_FRAMES` (10 кадров) — тот же принцип "живого окна", что и у игрока, вместо мгновенной проверки.

**Зрение и память (новое — раньше `detect_range` был просто радиусом):**

| Параметр | Значение |
|---|---|
| `vision_angle_degrees` | 55° — полный угол конуса зрения по направлению взгляда |
| `memory_duration` | 3.0 с — сколько ещё "помнит" игрока после потери из вида, идёт к last-known позиции |
| `alert_call_range` | 220 px — при обнаружении оповещает союзников в радиусе, даже если те игрока физически не видят |
| `stuck_give_up_time` | 0.5 с — если застрял в геометрии, преследуя last-known позицию, сдаётся раньше, чем истечёт вся `memory_duration` |
| `scan_interval` | 0.6 с — как часто озирается (меняет направление взгляда) в простое/поиске; не косметика — направление участвует в конусе зрения |

Точечный обход: на дистанции ≤ `attack_range` враг замечает игрока в любом случае, даже вне конуса (иначе вплотную промахивался мимо угла зрения).

**Подозрение и значки над головой (новое, Katana Zero-style).** Пока враг не `_aware`, каждый кадр проверяется более широкая "периферийная" зона (`_can_sense_player_peripherally()`), отдельная от боевого конуса зрения:

| Параметр | Значение |
|---|---|
| `suspicion_range` | 340 px (шире `detect_range`) |
| `suspicion_angle_degrees` | 110° (шире `vision_angle_degrees`) |
| `suspicion_confirm_time` | 0.8 с — столько нужно продержаться в периферийной зоне, чтобы враг перешёл в полноценный `_aware` |
| `suspicion_decay_time` | 0.5 с — столько нужно НЕ попадать в периферийную зону, чтобы счётчик подозрения сгорел |

Три значка коротко вспыхивают над головой врага (`_flash_alert_icon()`, ~0.6с показ + 0.25с затухание, `Label` с моноширинным шрифтом, без спрайтов):

| Значок | Когда | Цвет |
|---|---|---|
| `?` | Момент входа в периферийную зону (`_is_suspicious` стало true) | приглушённый лиловый `(0.62, 0.42, 0.62)` |
| `!?` | Момент перехода в `_aware` — либо обычное обнаружение конусом зрения, либо подтверждённое подозрение (`_on_newly_aware()`) | неоновый розовый `(1, 0.18, 0.66)`, тот же акцент, что у речевого пузыря |
| `!` | Момент начала атаки (`_start_attack()`) | красный опасности `(0.92, 0.15, 0.15)`, как экран смерти |

Значки — чисто визуальная надстройка, на боевую логику не влияют. Все параметры выведены слайдерами в админ-панели (F5 → вкладка AI врагов).

**Отряд (Squad):** враги координируются — `_find_engaged_ally_below()`, `_is_nearest_holder_for()`, `_should_hold_position()`. Есть `reinforce_hp_ratio = 0.5`: подкрепление приходит когда союзник на половине HP. `lower_level_y_threshold = 40` — распознавание врагов на другом этаже.

**Платформинг ИИ:** враг умеет прыгать через пропасти. `edge_check_ahead = 24`, `edge_check_depth = 60`, `max_jump_gap = 200`.

**Патруль (новое):** пока игрок не замечен, враг не стоит истуканом — ходит туда-сюда в радиусе `patrol_radius = 150px` от точки спавна, с паузами `patrol_pause_min/max = 1.0–2.5с` и вдвое медленнее (`patrol_speed_ratio = 0.5`). Патруль уважает те же edge-check'и, что и погоня — с уступа не спрыгивает.

**Очерёдность атаки (новое):** `_can_take_attack_turn()` — враг не бьёт, если кто-то из союзников уже бьёт, или если другой враг ближе к игроку и тоже готов атаковать. Не даёт всей группе бить одновременно; вместо этого не готовые к своей очереди враги встают на дистанции `attack_range × 1.4` (`_hold_at_standoff`), ждут.

**"Думающая" пауза (новое):** `think_duration_min/max = 0.15–0.4с` — после дискретного действия (атака, уворот, фланг) враг чуть медлит перед следующим решением, чтобы реакции не читались как мгновенные/роботические.

### Производные (расчёт)

- **TTK игрока по врагу:** 3 HP ÷ (1 урон / 0.5 с) = **1.5 с** чистого урона в базовом случае; реально варьируется ×0.75–×1.5 в зависимости от тайминга внутри окна попадания (см. Hit Zones)
- **TTK врага по игроку:** 3 HP ÷ (1 урон / 1.1 с) = **3.3 с**, с той же поправкой на Hit Zones
- **Разница скоростей:** 250 / 140 = **1.79×** в пользу игрока
- **Прыжок (110 px) vs рост врага:** перепрыгнуть удаётся, плюс работает фазовый проход (см. ниже)

## 3. Система коллизий

**Слои:**
- Слой 1 — игрок
- Слой 2 — враги
- Слой 4 — стены/земля

**Маски:**

| Состояние | `collision_mask` | `collision_layer` |
|---|---|---|
| Игрок обычный | 6 (враги + стены) | 1 |
| Игрок «фазовый» | 4 (только стены) | **0** |
| Враг обычный | 7 | 2 |
| Враг в уклонении | 4 | 0 |

**Ключевой механизм — фазовый проход.** Во время **переката И прыжка** игрок обнуляет и маску, и слой. Обнуление слоя обязательно: Godot проверяет коллизии независимо с каждой стороны, и если оставить `collision_layer = 1`, враг всё равно упрётся в игрока. Реализовано через счётчик `_phase_depth`, чтобы перекат и прыжок могли пересекаться и не восстанавливали коллизию раньше времени.

**Итог для игрока:** в NPC упираешься при ходьбе, **проходишь насквозь при прыжке и при перекате**.

**Анти-стакинг.** `_resolve_character_stacking()` есть и у игрока, и у врага: два `CharacterBody2D` могут застрять друг на друге в устойчивом равновесии. Метод ловит это по нормали коллизии и толкает верхнее тело вбок со скоростью `stack_push_speed = 140`.

## 4. Управление

| Действие | Клавиши |
|---|---|
| Движение влево | `A` / `←` |
| Движение вправо | `D` / `→` |
| Вверх | `W` / `↑` |
| Вниз | `S` / `↓` |
| Атака | `ЛКМ` / `Пробел` |
| Прыжок | **`J`** |
| Перекат | **`Left Shift`** или двойное нажатие `A`/`D` |
| Пауза | **`Esc`** (новое) |

> **Важно:** прыжок на `J`, а не на пробеле — пробел занят атакой. Это стоит пересмотреть при первом плейтесте с посторонним человеком.

**Пауза (`level.gd`).** `Esc` открывает/закрывает оверлей с кнопками CONTINUE / EXIT через `get_tree().paused = true`. Заголовка "PAUSED" больше нет (убран) — оверлей это просто затемнение фона + две кнопки. Не работает поверх экрана победы/смерти и пока открыта админ-панель (у неё своя заморозка через `AdminPanel.panel_open`).

Обе кнопки теперь используют те же пиксель-арт иконки, что и главное меню (`assets/MYASSETS/main menu/`, `continue.png`/`continueselect3.png`, `EXIT3.png`/`exitselect3.png`), с тем же поведением при наведении/фокусе (`_make_pause_icon_button()` в `level.gd`) и теми же звуками (`MENUSELECT.mp3`/`MENUSELECTAPPLY.mp3`). Звук клика переживает уничтожение оверлея тем же способом, что и в `men.gd` (`_play_pause_sfx()` репарентит `AudioStreamPlayer` в корень дерева перед тем как `_pause_canvas` освобождается) — без этого звук обрывался бы мгновенно, ровно та же проблема, что чинили в главном меню.

**Баг "CONTINUE вечно горит" (исправлено).** Первая версия проверяла подсветку каждой кнопки независимо (`is_hovered() or has_focus()`). Наведение мышью само по себе не передаёт клавиатурный фокус — так что CONTINUE (получает фокус по умолчанию при открытии паузы) оставался "в фокусе" и горел выбранным, даже когда курсор наводился на EXIT (которая параллельно тоже подсвечивалась через свой `is_hovered()`) — обе горели одновременно. Исправлено переносом паттерна из `men.gd`: общий `_pause_active_button` на весь оверлей — только одна кнопка может быть "активной", наведение на вторую явно гасит первую.

## 6. Админ-панель (F5)

Живая настройка баланса **без перезапуска игры**.

- Слайдеры по параметрам игрока и NPC (`PLAYER_SLIDERS`, `NPC_SLIDERS`)
- Тумблеры: неуязвимость игрока, неуязвимость NPC, режим AFK для NPC
- Кнопка спавна врага (`SPAWN_OFFSET = 220`)
- Кнопка сброса к дефолтам
- **Пресеты** сохраняются в `res://BAG/admin_presets`
- Быстрый переход между уровнями
- Переключение музыкальных треков

Пока панель открыта, `_physics_process` игрока замораживается — иначе клик по слайдеру засчитался бы как атака (ЛКМ = атака).

**Живая настройка требует сеттеров.** `set_strike_range()` и `set_max_hp()` существуют потому, что присвоение `strike_range` напрямую не меняет уже созданный `CollisionShape2D`. Любой новый настраиваемый параметр, влияющий на построенные ноды, нуждается в таком же сеттере.

Панель организована вкладками (`TabContainer`): игрок, бой NPC, ИИ NPC, пресеты. Кнопка "сохранить как дефолт сессии" рядом с обычным сохранением пресета. В слайдеры добавлены новые параметры Hit Zones (`attack_active_duration`, `sweet_spot_ratio` и оба множителя урона — у игрока и у NPC) и `parry_stun_duration` у NPC.

**Секции внутри вкладок (новое).** Раньше вкладка "Игрок" была одним сплошным списком из ~28 слайдеров без разбивки. Теперь каждый слайдер помечен полем `"cat"` (`PLAYER_SLIDERS`) или `"cat"`+`"sub"` (`NPC_SLIDERS`), и `_build_ui()` расставляет заголовки секций между ними — заголовки соответствуют реальным `@export_group` в `player.gd`/`samurai_npc.gd` (Прыжок/Стены/Рывок/Парирование/Окно удара у игрока; Атака/Уворот/Обходной манёвр у NPC-боя; Обнаружение/Подозрение/Платформинг/Темп реакции/Патруль у NPC-ИИ), а не выдуманы отдельно от кода. Заголовок — `_add_header()`: неоново-розовый текст с маркером `▍` и тонкой линией-разделителем под ним, с небольшим отступом сверху (кроме самого первого заголовка вкладки).

**Визуальное оформление (новое).** Константы `ACCENT_COLOR` (розовый, тот же что в `level.gd`) и `SECONDARY_COLOR` (голубой, как у "не видит" конуса зрения в `debug_visualizer.gd`) заведены прямо в `admin_panel.gd` (не импортируются из `level.gd`, т.к. это автозагрузка и должна работать даже до загрузки уровня). Фон панели — `Panel` со `StyleBoxFlat` и розовой левой рамкой (3px) вместо плоского `ColorRect`. Заголовок панели отделён от вкладок тонкой розовой чертой. Вкладки: активная — розовый текст, неактивные — приглушённый серый. Все `HSlider` перекрашены через общие (не по одному на слайдер) `StyleBoxFlat`-ресурсы `_slider_track_style`/`_slider_fill_style` — тёмная скруглённая дорожка с голубой заливкой вместо стандартного серого слайдера Godot.

### Уровень 5 — фон SynthCities (новое)

Пользователь закинул в `assets/` три новых пака: `cyberpunk city 2 files`, `cyberpunk-street-files`, `SynthCitiesGodot` — пока используется только последний.

**Важно про `assets/SynthCitiesGodot/`:** это не просто набор картинок, а целый отдельный мини-проект Godot (свой `project.godot`, свой `.godot/`-кэш с шейдер-кэшем). Внутри — демо-сцена `auto_scroller.tscn`, которая была **только фоном** (3 слоя параллакса + музыка), без пола/коллизий/спавнов — то есть "готового уровня" в паке не было, `level5.tscn` собран с нуля так же, как остальные уровни, просто с этим фоном.

**Файлы физически скопированы наружу, не используются из `SynthCitiesGodot/` напрямую.** Первая попытка сослаться на `res://assets/SynthCitiesGodot/CityLayers/...` из `level5.tscn` дала ошибку загрузки сцены "отсутствие зависимостей" — Godot **не импортирует ничего внутри папки, где лежит свой `project.godot`** (считает её границей отдельного проекта). Нужные 4 файла скопированы в обычную папку без вложенного `project.godot`: `assets/synthcities/CityLayers/{back,middle,foreground}.png` и `assets/synthcities/auto_scroller.gdshader`. Сама `assets/SynthCitiesGodot/` осталась нетронутой — фактически мусор в репозитории (как `Brawler Heat/` и `background/__MACOSX/`), можно удалить, если она больше не нужна как референс.

`level5.tscn` переиспользует всю дорожную геометрию `level.tscn` (асфальт/тротуар/фонари/коллизии через общий `RoadDetails` + `level.gd`), меняется только фон:

- **Первая версия использовала шейдер пака как есть** (`auto_scroller.gdshader`, сдвиг UV по `TIME`) — оказалось багом на практике: фон полз сам по себе даже когда игрок стоит на месте. Переделано на тот же принцип, что у остальных уровней — **`Parallax2D`** с `scroll_scale`, который двигается только вслед за камерой, а не по таймеру. Шейдер и его `.uid` удалены из `assets/synthcities/` как неиспользуемые.
- Три слоя `Parallax2D` + дочерний `Sprite2D` (масштаб ×3, позиция `(720, 295)` — тот же принцип, что у 5-слойного фона `level.tscn`, просто под 3 слоя вместо 5): `BgBack` (`CityLayers/back.png`, `scroll_scale = 0.1`, `repeat_size = 336`, `repeat_times = 14`), `BgMiddle` (`middle.png`, `scroll_scale = 0.35`, `repeat_size = 768`, `repeat_times = 7`), `BgForeground` (`foreground.png`, `scroll_scale = 0.7`, `repeat_size = 2064`, `repeat_times = 4`) — `repeat_size × repeat_times` у каждого слоя с запасом перекрывает весь пролёт уровня (`ROAD_MIN_X..ROAD_MAX_X` = 4320px), чтобы не было дыр на краях камеры.
- Собственный трек пака (`Music/cyberpunk-street.ogg`) **не подключён** — во всех уровнях музыку/эмбиенс всегда включает `level.gd::_play_level_audio()` через `MusicManager` (один общий трек на все уровни), отдельный `AudioStreamPlayer` в сцене уровня сломал бы это единообразие.
- `next_level_path` не задан (как у `level2`/`level3`/`level4` — в общую цепочку сейчас включён только `level.tscn → level2.tscn`).

Добавлен в список быстрого переключения уровней в админ-панели (F5 → LEVEL 5).

**Не сделано / на заметку:** два других новых пака (`cyberpunk city 2 files`, `cyberpunk-street-files`) не осмотрены и не использованы — если понадобятся, их сначала нужно проверить так же, как SynthCities.

### Спрайт игрока (новое)

### Главное меню — иконки (новое)

`men.tscn`/`men.gd` — меню теперь 4 пункта (NEW GAME, CONTINUE, SETTINGS, EXIT), все на пиксель-арт иконках из `assets/MYASSETS/main menu/` (`not selected/` — обычное состояние, `selected/` — состояние под курсором/фокусом). SPEEDRUN и LANGUAGE удалены из сцены целиком (были заглушками без реализации, `disabled = true`) — если понадобятся снова, придётся не только вернуть узлы, но и дорисовать под них иконки.

Механика: у каждой из 4 кнопок есть дочерний `TextureRect` "Icon" с текстурой "not selected", заданной прямо в `.tscn` (`anchor_right/bottom = 1`, `offset_* = 0` — заполняет всю кнопку, `expand_mode = EXPAND_IGNORE_SIZE`, `stretch_mode = KEEP_ASPECT_CENTERED`). `men.gd` при наведении мышью ИЛИ переходе фокуса клавиатурой (обе привязаны к общему `_on_button_focus`, как и раньше для курсора-`">"` и глитч-тряски) подменяет текстуру на "selected" и проигрывает звук наведения; дублирование по двум сигналам на одну и ту же кнопку (например клик — это одновременно и hover, и получение фокуса) гасится через `_current_button`. Клик по NEW GAME/SETTINGS/EXIT (CONTINUE выключена — `disabled = true`, сохранений ещё нет) дополнительно проигрывает отдельный звук подтверждения. Звуки: `main menu/sound selection/Hovered/MENUSELECT.mp3` (наведение) и `.../click/MENUSELECTAPPLY.mp3` (клик), оба через шину `SFX`. Звук клика переживает `change_scene_to_file()`/`quit()` через репарентинг в корень дерева (`_release_click_sfx()` в `men.gd`) — без этого сцена/процесс уничтожались раньше, чем звук успевал доиграть.

**Раскладка (обновлено).** Кнопки сейчас 234×118 (после нескольких итераций размера — начинали с 320×36 текстовых, потом 117×59 под убранные SPEEDRUN/LANGUAGE, потом пользователь попросил крупнее). `MenuList` заякорен единой точкой в центре экрана (`anchor_left/right/top/bottom = 0.5`, `offset_*` считаются от размера содержимого — сейчас `±117`/`±248`) — то есть весь блок кнопок буквально по центру экрана, а не смещён в сторону (раньше смещение было нужно, чтобы освободить место декоративному `Runner`, которого больше нет). Зазор между кнопками (`separation`) — `8`. Кнопки не растягиваются на ширину контейнера (`size_flags_horizontal = 0`, SIZE_SHRINK_BEGIN), поэтому при таком узком (по ширине кнопки) контейнере видимого эффекта "выравнивания по левому краю" уже не даёт — сейчас это просто "не тянуть шире, чем сама кнопка".

**Важно при ручном перетаскивании Icon в редакторе.** Один раз при перетаскивании узлов пользователем `Icon`-текстуры съехали и растянулись далеко за пределы своей кнопки (offset-ы вида `-553..-183` вместо `0..0`) — кликабельная зона (сама `Button`) осталась маленькой и на месте, а картинка визуально уехала в сторону и увеличилась, из-за чего клик перестал совпадать с тем, что видно на экране. Если снова увидишь несовпадение "картинка в одном месте, а клик срабатывает в другом" — проверь, что у `Icon` каждой кнопки `anchor_right/bottom = 1` и `offset_left/top/right/bottom = 0`.

### Игровой HUD игрока (новое)

`player_hud.gd` — дочерний `CanvasLayer` игрока (`layer = 9`), собирается полностью кодом в `_ready()` (без ручной разметки в `.tscn`, как и всплывающие окна save/load у `debug_hud.gd`). Опрашивает поля `player.gd` каждый кадр в `_process()` — сознательно без новых сигналов, т.к. ни один существующий сигнал не покрывает все случаи обновления (например промах парирования сбрасывает `parry_streak`, но не шлёт сигнал `parried`).

Расположен **в левом нижнем углу** — левый верхний уже занят всегда видимой панелью статистики `DebugHUD`, чтобы не перекрывались.

| Элемент | Что показывает |
|---|---|
| Ряд сердечек HP (обновлено) | Одно сердце на каждое целое очко `max_hp` (`ceili`), перестраивается только когда это число меняется (слайдер в админ-панели). Разбитых состояний-градаций нет — половинок сердца в артах пока нет, поэтому сердце либо целое (`HEALTH.png`), либо разбитое (`BROKEN HEART.png`): `floori(current_hp)` целых слева, остальные разбитые. Т.е. "получил урон = сразу видно разбитое сердце", а не дотягивает целым до полного израсходования очка |
| Заряды парирования | Ряд квадратных "пипсов", по одному на `max_parry_charges`; перестраивается заново только когда `max_parry_charges` реально меняется (например слайдером в админ-панели), а не каждый кадр |
| Стрик PERFECT-парирований | Текст `PERFECT xN`, появляется только при `parry_streak > 0`, коротко "пружинит" (scale-tween) при каждом изменении; когда стрик доходит до `perfect_streak_for_bonus` — меняет цвет на акцентный розовый (тот же порог, что даёт бонус-урон на следующий удар, см. `_next_hit_bonus` в `player.gd`) |

Заряды парирования и стрик-текст **пока плейсхолдер-геометрия** (ColorRect/Label в неоновой палитре проекта — `ACCENT_COLOR`/`DEATH_COLOR`/`FLASH_TEXT_COLOR` из `level.gd`), не настоящий пиксель-арт — как и было. HP-ряд эту стадию уже прошёл: теперь использует настоящие сердечки из `assets/MYASSETS/UI/hp/` (`HEALTH.png`/`BROKEN HEART.png`, исходник 64×64) вместо старой цветной полосы с текстом `"N / N"` — числовой подписи над сердечками больше нет (точное число по-прежнему видно в `DebugHUD` в левом верхнем углу).

**Размер сердечек (обновлено).** `HEART_SIZE = 128` (было 32, пользователь попросил минимум в 3 раза больше). По пути всплыл баг: увеличение `custom_minimum_size` у `TextureRect` само по себе ничего не меняло, т.к. `expand_mode` не был выставлен — с дефолтным `EXPAND_KEEP_SIZE` исходная картинка 64×64 рисуется в своём натуральном размере, просто по центру уже увеличенного бокса, а не масштабируется. Исправлено: `expand_mode = TextureRect.EXPAND_IGNORE_SIZE` на каждом сердце. Также `HEART_GAP = -60` (отрицательный, специально) — у самих PNG много прозрачных полей внутри 64×64 холста, так что даже нулевой зазор между боксами читался как большой зазор между видимыми сердечками; отрицательное значение стягивает боксы внахлёст, чтобы компенсировать эти поля, вместо того чтобы уменьшать `HEART_SIZE`.

**Хп-бар над головой игрока убран (новое).** Раньше `player.tscn` держал узел `HealthBar` (Back+Fill `ColorRect`) прямо над спрайтом, обновляемый через `hp_fill` в `player.gd`. Убран полностью — и узел из сцены, и все обращения к `hp_fill`/`_hp_bar_full_width` из `player.gd` (`_ready()`, `set_max_hp()`, `take_damage()`). Теперь HP игрока видно только в HUD в левом нижнем углу (сердечки выше). У NPC (`samurai_npc.gd`) свой `HealthBar` — этого изменение не касалось, он остался как есть (и `debug_visualizer.gd` продолжает читать его для оценки высоты глаз конуса зрения).

### Кровь (новое)

При смерти NPC (`samurai_npc.gd::_die()`) теперь спавнит кровь — без текстурного ассета, чисто процедурно, по референсу Katana Zero:

- **Всплеск** — одноразовый `CPUParticles2D` (`blood_spray_amount = 18` частиц), летит в сторону от игрока, спавнится сиблингом на уровне (не ребёнком NPC — тот делает `queue_free()` раньше, чем эффект успел бы доиграть) и сам себя удаляет по таймеру после окончания.
- **Декали привязаны к полу под точкой смерти, не к телу NPC (важный фикс).** Изначально декали ставились у `global_position` самого NPC в момент смерти — а смерть часто наступает в воздухе (прыжковая атака, бой на краю платформы), из-за чего пятна оказывались подвешены выше настоящего пола или вообще проваливались мимо видимых блоков ("кровь просто улетает вниз"). Теперь `_find_ground_below()` пускает луч вниз (`collision_mask = 4`, тот же слой стен/пола, что и в `_has_ground_ahead`/`_has_safe_landing_ahead`) от точки смерти и находит реальную поверхность твёрдого блока; `blood_decal_count = 4` неровных пятна-полигона (`_make_blood_blob`) ставятся именно на неё, приподнятые на половину своего радиуса, чтобы не проваливаться визуально в текстуру пола. Если под точкой смерти нет пола вообще (упал в яму) — декали не спавнятся, вместо подвешивания в пустоте.
- Направление всплеска — приближение (в код не прокинут реальный атакующий/направление удара, берётся направление "от игрока"), этого достаточно, раз игрок почти всегда и есть источник смерти.
- **Осознанно не сделано:** нет кап/пулинга декалей — при очень длинном забеге с большим числом килов они будут копиться без ограничения. Это база механики, а не финальная система; если станет проблемой перформанса/визуального шума — добавить счётчик на уровне и удалять старые декали при превышении лимита.

## 10. Что ещё не сделано

**Направленные атаки.** В `InputMap` есть `move_up` и `move_down`, и по задумке `W + ЛКМ` = удар вверх, `S + ЛКМ` = удар вниз. **В коде этого всё ещё нет** — телеметрия пишет только `"FORWARD"`. Парирование работает чисто по совпадению тайминга, направление не учитывается. Актуальный статус не изменился с прошлого аудита.

**Зоны хитбокса — сделано, но не совсем так, как обсуждалось.** Раньше здесь стоял пункт "не сделано" (обсуждались три зоны WHIFF/ACTIVE/SWEET SPOT с разным уроном по дистанции). Реализованный вариант — **не по дистанции, а по времени**: окно активности 0.12с, ранняя часть (35%) = sweet spot ×1.5, поздняя = ×0.75 (см. раздел 2, "Зоны попадания"). Зеркально у игрока и у врага. Если исходная идея была именно про дистанцию/позиционирование, а не про тайминг — это разошлось с планом и стоит явно обсудить с пользователем.

**Диалоги.** Больше не "ноль диалогов": у самурая-врага теперь одна реплика при первом обнаружении игрока (`dialogue/samurai_intro.dialogue`, речевой пузырь над головой). Полноценного диалогового дерева, веток или разговоров с другими NPC всё ещё нет — это первый рабочий пример, не система.

**Офисное здание.** Статус с прошлого аудита не менялся — в работе, геометрия требует пересчёта. Не путать с `level4.tscn` (это отдельный уровень для стеновой механики, не офисное здание).

**Плейсхолдер-анимации урона/смерти игрока (новое).** Новый спрайт-пак "male hero" не содержит кадров hurt/death — `hurt`, `hurt_flash` и `death` играют одиночный статичный кадр вместо анимации. Заметно на глаз при получении урона/смерти.

**Известная проблема баланса — похоже, исправлена.** Раньше: окно контратаки после парирования (стан 0.3с = 18 кадров) было короче атаки игрока (0.5с = 30 кадров) — попасть в стан было физически невозможно. В текущем коде `parry_stun_duration` у врага поднят до **0.55с** (33 кадра) — комментарий в коде прямо ссылается на эту проблему и говорит, что она исправлена этим изменением. **Формально ещё не подтверждено телеметрией** — стоит проверить по логам, что окно контратаки реально используется игроками после парирования, а не просто арифметически возможно.

## 11. Правила работы над проектом

- Пользователь не программист — объясняй кратко, словами, без жаргона
- Код только GDScript, Godot 4 синтаксис
- Всегда говори какие именно ноды/кнопки нажать в редакторе Godot
- Итерация важнее совершенства: рабочий прототип → потом красота
- Не более 2–3 параметров баланса за раз, иначе непонятно что сработало
- Проверяй изменения запуском игры и скриншотом
- Если задача большая — сначала план одной строкой, потом реализация
- При конфликте с решениями выше — скажи об этом прямо, не молчи

**Живая настройка.** Любой новый боевой параметр стоит сразу выводить в админ-панель слайдером — так его можно крутить в игре, а не пересобирать сцену.

**Телеметрия — источник истины.** Прежде чем менять баланс «на ощущениях», посмотри что показывают логи. Комментарий в `player.gd` про тир BARE — прямой пример: телеметрия показала, что BARE это ~86% всех успешных парирований, из-за чего у самого частого исхода вообще не было визуального фидбека.
